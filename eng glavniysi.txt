# ZEROLAX — FINAL CLIENT REQUIREMENTS INTEGRATION

You are working on the existing ZEROLAX educational Telegram Mini App project.

Your task is to update and integrate the final client decisions below into the existing architecture, backend, frontend, database, admin panel, and testing system.

## 2. FINAL EXAM AND CERTIFICATE RULES

Implement the following score policy:

| Score | Result |
|---|---|
| Below 40 | Book must be studied again |
| 40–49 | Admin-configurable result policy |
| 50–70 | Recommend reviewing the material; next book remains locked |
| 71–79 | Next book unlocks; no certificate |
| 80–100 | Next book unlocks and certificate is issued |

Important:
- Certificate threshold is exactly 80 points.
- A score of 80 or higher qualifies for a certificate.
- A score of 71–79 unlocks the next book but does not qualify for a certificate.
- A score of 50–70 does not unlock the next book.
- Below 40 requires repeating the book.
- The 40–49 range must be configurable by the admin. Do not invent a fixed policy for it.

Make all thresholds configurable in the admin panel, with the above values as defaults. The admin must be able to change them later.

## 3. RETAKE POLICY

The client has confirmed: **one retake per exam**.

Implement this rule consistently for:
- Topic tests
- Intermediate exams
- Final book exams

Requirements:
- Each user receives one initial attempt and a maximum of one additional retake for each exam.
- Maximum attempts per exam: 2.
- Display the number of remaining attempts before the user starts.
- Store each attempt separately, including score, answers, start time, finish time, and status.
- Do not allow the frontend to reset or bypass attempt limits.
- Enforce the limit on the backend and database.
- Prevent duplicate submissions and race conditions.
- Admins may have a separately permission-controlled ability to grant an additional attempt. Every override must be recorded in the audit log.
- If an exam is passed, do not offer an unnecessary retake unless the admin explicitly enables it.

## 4. TOPIC TEST

The client has confirmed: **10 questions per topic test**.

Requirements:
- Each topic test contains exactly 10 questions.
- Questions must be selected randomly from the question bank belonging to that topic.
- Avoid duplicate questions within the same attempt.
- Store the selected question IDs when the attempt starts.
- If fewer than 10 suitable questions exist, do not start an incomplete test. Show a clear message to the user and notify the admin.
- Calculate scores on the backend.
- Save answers and results securely.
- Apply the one-retake policy.

The admin must be able to add, edit, and organize topic questions.

## 5. INTERMEDIATE AND FINAL EXAMS

Keep the existing exam structure:

### Intermediate exam
- After every 10 topics, create an intermediate exam.
- Exactly 20 questions.
- Questions are randomly selected from the 10 topics covered in that block.
- Apply the one-retake policy.

### Final book exam
- Exactly 20 questions.
- Questions are randomly selected from the entire completed book.
- Apply the one-retake policy.
- Apply the final score rules from Section 2.
- Unlock the next book only when the configured passing threshold is reached. Default: above 70.

## 6. PREMIUM — TWO ACCESS METHODS

The client has confirmed that Premium must support BOTH methods:

### Method A: Admin-granted Premium
- Admin can manually grant Premium to a user.
- Admin can set the start date, expiration date, and duration.
- Admin can revoke or extend Premium.
- Record the admin responsible for each change.
- Log all changes in the audit log.

### Method B: Paid Premium subscription
- Build a real payment integration architecture.
- Use a payment-provider abstraction so a supported provider can be connected without rewriting the subscription system.
- Do not invent payment credentials or pretend that a payment succeeded.
- Verify payment status on the backend using the provider's official verification mechanism or webhook.
- Never activate Premium based only on a frontend success message.
- Prevent duplicate payment processing and duplicate subscription activation.
- Store payment transaction ID, provider, amount, currency, status, and timestamps.
- Handle successful, pending, failed, refunded, and expired transactions.
- Activate Premium only after verified payment.
- Keep payment secrets on the backend.

### Premium access rules
- Free users can access topics 1, 2, and 3 in each book by default.
- Topics 4 onward require active Premium.
- Admin can configure the free-topic limit for each book.
- Admin-granted and paid Premium subscriptions must use the same access-control system.
- When Premium expires, paid content becomes locked again, but the user's completed topics and exam history must remain saved.
- Do not delete user progress when a subscription expires.

Do not choose a payment provider, subscription price, or subscription duration without an existing project configuration or explicit client decision. If these details are missing, implement the provider-ready architecture and leave configuration clearly marked as pending.

## 7. CERTIFICATE GENERATION

Generate a certificate when a user achieves 80 points or higher in the final book exam.

Certificate must include:
- Student's full name
- Grade/class
- Book name
- Exam score
- Completion date and time
- Time spent on the exam
- Unique certificate ID
- QR code for verification

Requirements:
- Generate a PDF certificate.
- Store the PDF securely.
- Create a public certificate verification page.
- The QR code must open the verification page.
- The verification page must show only public-safe certificate information.
- Do not expose phone numbers, addresses, private user data, or internal database identifiers.
- Prevent duplicate certificate generation for the same qualifying exam completion.
- Allow admins to inspect and revoke certificates with an audit record.
